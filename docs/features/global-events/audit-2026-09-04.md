## 1. 實測證據（2026-09-05 00:0x 台北，`intel.global_event_collector_run_receipts` LIMIT 30）

```
last 48h:  failed source_or_stage1_failed = 38 ／ accepted = 14
09-03 22:31 → 09-04 11:31  連續 14 輪 failed（finish_reason='error', content_length 1.4k–8.2k）
其餘 failed：429 Too Many Requests ×6
max(observed_at) = 2026-09-03 18:45 台北；max(available_at) = 09-04 23:38；lag = 1 day 05:18
```

解讀：accepted 的輪次都在 drain 舊 pending queue（`available_at` 有前進），但 checkpoint 自 09-03 18:45 起沒推進（`observed_at` 不動）。handoff 寫的「落後約 14 小時」已惡化到 29 小時，且會繼續擴大。`finish_reason='error'` 是 OpenRouter provider 端錯誤，不是 GDELT 上游延遲。receipts 不帶 chunk 身分，「同一 chunk 每小時重試」是推論：證據是連續 8 輪 error 的 content_length 都落在 4.2k–4.6k，與同一批 pending 重送一致。

## 2. Collector（`data-collectors/collectors/global_events.py`，1950 行）

資料流：每 60 min 抓 GDELT GKG masterfilelist（standard＋translation）→ 逐 15-min slot 最多 8 檔／stream → 只解析 metadata → 標題 fingerprint 分群 → regex 路由 → immutable batch（candidate_id = hash(fingerprint, first_slot, last_slot)）→ 先寫 `routing_pending.json` → 取前 cap 筆以 10 筆/chunk 呼叫 OpenRouter Qwen（chunk 結果快取）→ 上 S3 handoff → collector 自己經 `supabase_writer` 寫 receipts 與 `public.ingest_global_event_candidates()` → `intel.global_event_candidate_observations`。剩餘 pending 下輪只 drain 不抓新檔；全 drain 完才推 checkpoint。Publisher 不經此 collector（`production_publishable` 三處寫死 False）。
