# CCTV 車輛辨識微調與路口還原：路線規劃

更新：2026-09-29。前情與證據見 [cctv-xinyi-recovery-2026-09-29.md](cctv-xinyi-recovery-2026-09-29.md) §13。本文件是規劃，不是已完成的成果；裡面的時程與目標值都是待驗證的假設。

## 0. 一句話結論

微調本身**技術上不難**：Ultralytics 幾行指令、雲端一張 GPU 約1–3小時就能訓完一版。真正花時間的是**資料**：收集夠多樣的畫面、標註一致、切分時不要洩漏答案、授權與隱私。整條「辨識 → 道路模型 → 路口還原」是**長期路線**，可以切成幾個兩週內可完成、各自可驗收的階段。

## 1. 為什麼需要微調（已有證據）

同一批晚間62張、使用者修正的231框（汽車155、機車67、公車9）：

- 現成 COCO 模型 n／s／m、提高解析度、切塊推論，**機車 recall 都只有0–1.5%**；汽車最高79%（m，運算約7倍）。
- 67台機車中63台被看成「person」（騎士），信心只有0.05–0.12；用規則補救會多出約290個誤判框，不可用。
- 結論：問題在於模型沒學過「台灣監視器視角、夜間、密集機車」這種畫面，屬於**資料分佈落差**，微調正好能處理這種問題。白天尚未驗證。

## 3. 除了微調，還有哪些路（可並行）

1. **直接用政府流量資料**：若目標是「路口狀況數字」，可先接官方流量偵測資料（例如上述 AI 路口偵測器，或 TDX 車輛偵測器 VD），CCTV 只負責視覺化。最快，但不能自己控制涵蓋範圍。
2. **自動預標註＋人工修正**：用大模型（m）或開放詞彙偵測模型（Grounding DINO、Gemini 等能輸出框的模型）先標，再由人修正。可大幅減少標註時間，是微調的加速器，不是替代品。
3. **混合公開資料集**：先用公開機車資料訓練，再用少量台灣 CCTV 資料微調。
4. **試用商用服務**：當基準對照，了解業界水準。

建議：**微調（主線）＋2（加速標註）＋1（驗證來源）**。

## 4. 主線：微調路線（階段、產出、學習重點）

### 階段0：定義與治理（半天）
- **類別**：`car`、`motorcycle`（騎士＋車算一框）、`bus`、`truck`；停放的機車也標，另加屬性 `parked`（之後可用來判斷停車）。
- **指標**：各類別在**固定precision（例如≥80%）下的recall**、mAP50；日／夜、各鏡頭分開報告。驗收門檻要在看過 baseline 後再定，不要事先拍腦袋。
- **治理（需使用者決定）**：
  - 訓練需要保存**不模糊影像**，保留期限與位置要定。
  - 若上 Google／AWS，就是把影像上傳到外部服務，需先確認公開 CCTV 影像的再利用條件（臺北市交工處對錄影影像提供有[說明](https://bote.gov.taipei/News_Content.aspx?n=20A2BA930381C524&s=20461E7AABE69B6F)，需逐條確認）。
  - **模型授權**：Ultralytics YOLO 為 AGPL-3.0，研發與內部使用也可能需要企業授權，除非整個專案開源（[Ultralytics License](https://www.ultralytics.com/license)）。學習與開源用途沒問題；若日後要商用，改用授權寬鬆的模型（例如 RF-DETR、RT-DETR 系列，使用前再確認授權條款）。

### 階段1：收集資料（1–2天，需授權排程）
- **鏡頭**：3支信義路之外，再挑5–7支不同型態的鏡頭（大路口、機車多的路段、高架下、遠景），**多樣性比張數重要**。
- **時段**：早尖峰、午間、晚尖峰、夜間；有下雨更好。
- **取樣**：每場擷取60秒，每2–3秒取1張新內容畫面（去掉重複和太相似的畫面），避免同一台車被訓練好幾十次。
- **目標量**：約400–600張、機車實例5,000以上（第一版可以先200張試跑）。
- **做法**：沿用 `capture.py --blur-kernel 0 --output ...`；排程用 macOS `launchd` 或 cron，只在電腦開著時跑。**建立排程前需使用者授權。**

### 階段2：標註（1–3天）
- **工具**：本機 CVAT 或 Label Studio（不上傳），或沿用本 POC 的 `annotate.html`（已能修框，需擴充匯出 YOLO 格式）。
- **預標註**：先用 m 模型標汽車；機車用「低信心 person」候選輔助，由人確認。
- **標註規範**（最重要的一頁文件）：框要包住騎士和車；小於約8像素高的標「忽略區」；遮擋超過一半照樣標但加註記；停放的車也要標。
- **品質**：隨機抽10%給第二人獨立標，量兩人的一致度。

### 階段3：切分（重點：避免答案洩漏）
- **不要隨機切畫面**：相鄰畫面幾乎一樣，隨機切會讓測試分數虛高。
- 依**鏡頭與時段**切：例如保留1–2支鏡頭完全不進訓練，當作「沒看過的鏡頭」測試。

### 階段4：訓練
- **基準**：先記錄現成模型在測試集上的分數（第1節的做法）。
- **微調**：從 COCO 預訓練的 s 模型開始，imgsz 960、約50–100 epochs，開啟資料增強（亮度、模糊、雨天模擬）。
- **平台（擇一，也是學習重點）**：
  - Google Colab 或 Vertex AI Workbench／Custom Training：最貼近程式碼，適合學原理。
  - Vertex AI AutoML 影像物件偵測：不用寫程式，可和自訓模型比較（[官方範例](https://github.com/GoogleCloudPlatform/vertex-ai-samples/blob/main/notebooks/official/automl/automl_image_object_detection_online_prediction.ipynb)）；使用前確認[停用公告](https://cloud.google.com/vertex-ai/docs/deprecations)，AutoML 影片與文字版已停用。
  - AWS SageMaker Training Job：自備 Ultralytics 容器，單張 A10G（如 ml.g5 系列）即可（[AWS 範例](https://github.com/aws-samples/amazon-sagemaker-train-and-deploy-yolov5)、[Ultralytics×SageMaker](https://docs.ultralytics.com/integrations/amazon-sagemaker)）。
  - 費用依機型與時數而定，開跑前用官方計價工具估算，不在此預估數字。

### 階段5：評估與錯誤分析
- 用沒看過的鏡頭與時段報告各類別的 PR；逐張看錯誤（漏、誤、類別混淆），把錯誤分類。
- 把新模型接回管線，用 `score_boxes.py` 與既有人工真值比較，再重新調追蹤設定（D／E）。

### 階段6：迭代（主動學習）
- 挑模型最沒把握的畫面優先標註，通常比隨機多標更有效。每一輪都記錄資料版本、模型版本與分數。

## 5. 目標2：衛星圖＋道路模型

**觀念修正**：「行進方向」和「停下來的車」**不是靠微調偵測模型學的**，而是由「追蹤軌跡＋道路幾何」算出來的。偵測模型只負責找到車和分類。

1. **定位與朝向**：每支鏡頭用正射圖（國土測繪中心）標出路口、車道、停止線、斑馬線，確認鏡頭位置與朝向。
2. **地面校正**：影像與正射圖之間至少4個擬合點＋獨立檢查點，算單應性矩陣，報公尺殘差（工具已在 `validation.html`）。
3. **道路模型**：每個路口定義「進入臂→離開臂」的轉向組合與車道方向，存成 GeoJSON。
4. **方向與停車**：軌跡投影到地面，用位移算方向與速度；低於門檻超過N秒就是停等或停車。
5. **鏡頭轉動偵測（已踩到）**：9/29 晚間批次的視角和下午不同。需要每次擷取先比對參考畫面，視角變了就停用舊校正、重新校正。

## 6. 目標3：整合還原路口

1. 地面軌跡配對道路模型 → 每5或15分鐘各轉向的車數，並附不確定範圍。
2. **驗證**：與臺北市 AI 路口流量偵測器（若同路口）或人工計數比對。
3. **視覺化**：看得到的部分畫觀測軌跡，看不到的部分用校準過的流量做模擬，並明確標示是模擬。
4. 跨鏡同一台車的串接不列入目標（第13節的理由）；以流量層級串接。

## 7. 時程（假設，視每階段驗收結果調整）

| 期間 | 範圍 | 驗收 |
|---|---|---|
| 第1–2週 | 階段0–5：第一版微調模型 | 沒看過的鏡頭上，機車 recall 明顯高於 baseline（門檻看完 baseline 再定） |
| 第1–2個月 | 1–3個路口：校正、道路模型、轉向量 | 與官方或人工計數比對，報誤差 |
| 3–6個月以上 | 多路口、近即時、鏡頭轉動監測、模型版本管理 | 持續運轉的健康指標 |
